# 東方符卡大戰 (Touhou Spell Card War)

爐石戰記式的東方同人卡牌對戰，**純 HTML + CSS + JS**，丟上 GitHub Pages 就能玩，存檔在 localStorage。
本版定位是 **規則驗證原型 v0.1**：先確認機制好不好玩，再談美術與擴充。

## 玩法

開啟 `index.html` 即可。GitHub Pages、XAMPP（`http://localhost/TouhouSpellCardWar/`）、
直接用瀏覽器開 `file://` 三種方式都測過可以正常遊玩與存檔。

- 單機對戰 AI，8 位英雄（紅魔鄉～永夜抄自機組）
- 8 副預設牌組（唯讀、隨版本更新，對戰時可直接選用）
- 牌組編輯器：自己的牌組可新增／編輯／刪除，也能從預設複製一份來改
- 英雄選擇畫面：分作品分頁、可搜尋技能，新增英雄會自動出現
- 費用曲線、自動補滿、牌組碼匯出匯入
- 戰績統計、對局中斷續玩

## 核心規則

| 項目 | 內容 |
|---|---|
| 勝利 | 把對手英雄血量打到 0；牌庫抽完後每次抽牌受累加疲勞傷害 |
| 資源 | 靈力，每回合上限 +1（最多 10）並回滿 |
| 場地 | 前排角色列 5 格、後排結界列 5 格、場地區 1 格（雙方各一） |
| 卡種 | 角色 / 符卡（一次性） / 結界（永續） / 場地 / BGM |
| 牌組 | 主牌組 40 張 + BGM 欄 1 張。同名卡最多 4 張，中立卡 + 該英雄職業卡，專屬卡限 1 張 |
| BGM | 放在**獨立的 BGM 欄**（不算主牌組 40 張、不會被抽到）。你的第 4 回合自動進手。全場只有一個播放器，新的會蓋過舊的（含對手的）；被蓋過的會回到擁有者手上。發動後對手接下來 2 個回合不能發動 BGM |
| 先手 | 起手 3 張。優勢來自行動順序本身 —— 前兩回合每一步都領先一拍 |
| 後手 | 起手 4 張、英雄血量 +4、「後之先」（靈力上限達 2・4・6・8 時各抽 1）|

關鍵字：`疾走` `守護` `飛行`（無視守護）`隱行` `彈幕`（濺射相鄰）
`貫通`（溢出傷害打臉）`吸精`（造成傷害時回血）`捨身`（英雄本回合受過傷）
`連奏 N`（本回合第 N 張符卡）`追擊`（本回合第二次以後的攻擊）`符卡使 N`

關鍵字不需要記憶 —— 滑鼠移到卡片上就會列出該卡用到的每個關鍵字說明。
辭典在 `js/keywords.js`，加一筆就會同時反映到卡面提示與規則說明頁。

> 成為英雄的原作角色同時也有**角色卡版本**（例如愛麗絲既是英雄也能被召喚到場上），
> 這類專屬卡每副牌組限 1 張。

## 測試

```bash
npm install          # jsdom + puppeteer-core（借用系統已安裝的 Chrome）
npm test             # 平衡循環賽 + jsdom 邏輯測試 + 真瀏覽器測試
npm run lint         # 只檢查英雄技能是否有完全上位互換
npm run balance      # 只跑平衡量測
npm run browser      # 只跑真瀏覽器測試（可傳網址）
npm run cards        # 重新產生 docs/卡表-現況.md
```

`chrometest.js` 用 `page.click()`，也就是**真實座標 + 命中測試**。這點很重要：
jsdom 的 `element.click()` 直接派發事件、無視遮擋，所以曾經漏抓過
「`#overlay` 因為 CSS `display` 蓋過 `[hidden]` 而永遠擋在畫面上、吃掉所有點擊」這個 bug。
凡是動到版面、`z-index`、`hidden` 切換的改動，都要跑這支。

`selftest.js` 會跑完整英雄循環賽（每一對英雄雙方各先手），輸出先手勝率、
平均回合數與各英雄勝率。**改動任何卡片數值後請重跑**，數字會馬上告訴你踩到什麼。

### 目前平衡數據（560 場）

- 先手勝率 **45.7%**
- 平均 **19.7** 回合
- 英雄勝率 29%～59%

⚠️ 這是 **AI 自我對戰**的數據，而且是用**簡單難度**跑的（平衡數字要跨版本可比，
所以基準固定在簡單）。簡單難度是 1-ply 貪心，
**看不到「這一步是為了下一步鋪路」**，所以會系統性低估某些英雄技能。實測技能使用率：

```
博麗靈夢 0.24  愛麗絲 0.27  妖夢 0.23  蕾米 0.20  紫 0.20   ← 立即有場面效果，AI 會用
魔理沙  0.08  咲夜   0.05  幽幽子 0.03                      ← 為後續鋪路的，AI 幾乎不用
```

因此**幽幽子（38%）與咲夜的數字被低估**，要判斷這兩位請實際手玩。
反過來說，看到某位英雄異常低時，先跑這個使用率診斷，不要直接改數值 ——
霧雨魔理沙就曾因此被誤判過一次。

每位英雄的流派設計見 [docs/builds.md](docs/builds.md)。

## AI 難度

兩種難度**共用同一份搜尋程式**，差別只有 `js/config.js` 裡的參數：

```js
var AI_LEVELS = {
  easy: { beam: 1,  depth: 1,  foresee: false },  // 展開一層、只留一個 = 單步貪心
  hard: { beam: 12, depth: 10, foresee: true  }   // 整個回合 ＋ 對手回擊
};
var AI_FORESEE = { topN: 3, beam: 4 };            // 前瞻幾個候選 / 模擬對手時的束寬
```

「ply」指的是**一方的一整個回合**，不是一個動作 —— 困難就算在一個回合裡算了 9 步組合，
那仍然是 1-ply。`foresee` 打開的才是第 2 個 ply。

`beam:1, depth:1` 在數學上就等同於原本的貪心 —— 這是刻意的，
兩邊不會分岔成「改了一邊忘了另一邊」。改動後跑 960 場，簡單難度的每一個
勝率數字都與改動前完全相同，可以確認這件事。

### 困難做對了什麼

**1. 視野從一個動作變成一整個回合。** 原本 `aiNextAction()` 每次只算一步，
所以「先強化再打臉」「先用大的清掉守護、小的才能繞過去」這種前一步看起來虧的線
會被 `base + 0.01` 這道門檻直接濾掉。

**斬殺是免費附贈的** —— `evalState` 對獲勝回傳 `1e6`，改成整回合搜尋之後，
只要有任何一條序列打得死，葉節點就會撿到，不必寫獨立的斬殺判斷。

**2. 2-ply 前瞻（`foresee`）。** 把最好的幾個候選結局各往前推一個回合，
看對手回擊之後盤面變成什麼樣，再回頭決定這一回合怎麼打。

**對手只模擬「攻擊」，不模擬出牌 —— 這是刻意的限制，不是偷懶。**
`cloneState` 是整個 state 複製，模擬對手出牌就會用到他手上的牌和他下一張抽牌，
等於 AI 偷看玩家的手。場面是公開資訊，所以只推演攻擊不算作弊。
（現在的評估函式也只用 `op.hand.length`，從不看內容。）

有一個容易踩的坑：前瞻後的分數是「對手回擊完」的分數，跟「什麼都不做」的分數
不是同一把尺。直接比會導致所有選項都被否決、AI 整回合發呆 ——
所以基準線也要跑一次前瞻（假設我這回合什麼都不做）。

### 兩個機制都是通用的

搜尋與前瞻都只用 `enumActions` / `applyAction` / `evalState`，完全不認識任何一張卡。
**以後新增的卡自動被納入，不需要為 AI 補任何東西。**

### 量測到什麼、又砍掉了什麼

困難對簡單穩定落在 67–73%。但把兩個機制拆開單獨量，結果不一樣：

| | 對上「關掉它」的對照組 | 有沒有情境靠它 |
|---|---|---|
| 回合層級搜尋 | 決定性（關掉就退回簡單） | 情境 1、3 |
| 2-ply 前瞻 | 51.8% ±5.0（384 場，跨過 50%）| **情境 5** |
| ~~威脅評估~~ | 52.6% ±5.0，六種權重全落在 49.6–52.0% | **一個都沒有** |

**威脅評估已移除。** 它想估「對手下回合能打到我臉上多少」，但那跟 `unitVal`
重複計算了同一件事 —— 我這回合能改變它的方式基本上只有「殺掉對手的角色」，
而那早就算在角色估值裡。它想近似的東西，現在由前瞻用真正的模擬做到。

**前瞻保留了**，雖然總體也不顯著。理由是它有一個 1-ply 無論搜多深都解不了的
具體行為（情境 5：打臉會被反殺時該先清威脅），而威脅評估連一個都舉不出來。
成本 127ms 平均、827ms 最久，可以接受。

### 成本

實測分支數平均 10.7（最多 64）、每回合 3.3 步（最多 9），`cloneState` 一次 0.047ms。
每個 AI 回合規劃一次的耗時：

```
1-ply（只搜尋自己的回合）        平均  76 ms　最久  653 ms
2-ply 只模擬對手攻擊 前 5 名      平均 126 ms　最久  718 ms　×1.7
2-ply 只模擬對手攻擊 前 8 名      平均 171 ms　最久 1360 ms　×2.3
2-ply 完整模擬對手回合 前 3 名     平均 143 ms　最久  803 ms　×1.9  ← 會作弊，沒有採用
```

上面是 Node 的 `vm` 沙箱，比瀏覽器慢一個量級。**Chrome 裡的實測**（40 局、658 次規劃）：

```
簡單　平均  0.4 ms　中位  0.3 ms　p95   1 ms　最久   4 ms
困難　平均 17.9 ms　中位 10.6 ms　p95  60 ms　最久 208 ms
```

介面本來就有 **700ms** 的 AI 動作間隔，連最差的 208ms 都塞得進那個空檔，
玩家感覺不到延遲。`tools/ai-scenarios.js` 的情境 6 是效能防線
（平均 < 400ms、最久 < 3000ms，以 Node 為準），
避免以後有人把 `beam` 或 `AI_FORESEE` 調大就悄悄變卡。

**不要把 topN 和對手束寬同時開大** —— 前 8 名 × 束寬 12 會飆到 5 秒。

### 困難**不會**改善的事

魔理沙那三張結界要下一回合才回本，而束搜尋的視野是「這一回合結束」——
結界打出去的當下盤面沒有變化，評估仍然是 0，困難一樣不會打。
**困難改善的是斬殺、換牌順序、combo 線、打臉時機；長線引擎的估值不在裡面**，
那需要 2-ply 或給卡片標註提示，是另一個題目。
